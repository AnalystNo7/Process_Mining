# 00. Обзор проекта Process Mining MVP

## Назначение документа

Этот файл — корневой документ ТЗ. Здесь — цели, термины, стек, ссылки на остальные файлы. Перед началом любой задачи Claude Code должен прочитать этот файл.

## Цель проекта

Создать **production-ready** систему process mining для анализа цифровых логов бизнес-процессов. Основные источники данных — российские СЭД (TESSA), ITSM (Naumen) и аналогичные системы. Главная аналитическая задача — выявление **узких мест** (bottlenecks) и **зацикленностей** (rework) в процессах для последующей оптимизации.

В качестве функционального ориентира используется внутренняя система process mining Сбербанка и публичные отчёты Газпром ЦПС по анализу процесса согласования договоров в системе TESSA.

## Целевые пользователи

- **Бизнес-аналитики** (основные пользователи) — загружают логи, строят дашборды, ищут проблемные места процессов, готовят отчёты руководству.
- **Менеджеры/руководители** — просматривают готовые дашборды, оценивают эффективность процессов.
- **Администраторы** — управляют пользователями, ведут общие справочники, имеют полный доступ ко всем проектам.

Объём аудитории: **10-20 пользователей** в первой версии.

## Ключевые сценарии использования (use cases)

1. **Загрузка лога процесса.** Аналитик получает выгрузку из СЭД (Excel-файл), загружает в систему, мапит колонки на стандартные поля, размечает подразделения по ролям, получает виртуальный датасет для анализа.
2. **Анализ зацикленностей (ping-pong).** Аналитик строит таблицу повторов операций, видит ТОП-N операций с наибольшим процентом повторов, сравнивает длительность кейсов с повторами vs без.
3. **SLA-комплаенс.** Аналитик настраивает SLA-справочник (норматив длительности по операциям/ролям), система автоматически считает процент просрочек, выводит таблицу нарушений.
4. **Граф процесса.** Система строит граф ТОП-N путей процесса, аналитик исследует структуру, видит узкие места, помечает их аннотациями.
5. **Кастомные дашборды.** Аналитик собирает дашборд из готовых виджетов (KPI-карточки, графики, таблицы, графы), применяет фильтры, сохраняет, открывает повторно через неделю/месяц.
6. **Экспорт результата.** Аналитик сохраняет дашборд или отдельный виджет как PNG для вставки в презентацию.

## Что НЕ в скоупе MVP

- Предсказательная аналитика (predictive process mining) — прогнозирование сроков, аномалий.
- Conformance checking как формальная сверка с эталонной BPMN-моделью.
- Финансовая оценка стоимости rework (расчёт ФОТ × процент повторов в рублях).
- Сравнение нескольких процессов между собой в одном дашборде.
- Коннекторы к внешним системам (прямое подключение к TESSA/Naumen). Загрузка только из xlsx.
- Real-time стриминг событий. Только batch-загрузка файлов.
- Понятие "цикл согласования" как отдельная сущность с нумерацией. Учитываем только повторы операций.
- Расчёт стоимости rework в рублях (нет в MVP).
- Социальная сеть исполнителей (social network mining).
- Мобильная версия. Только desktop-браузер.

## Архитектурные принципы

1. **Production-готовность важнее скорости разработки.** Никаких Streamlit, никаких Jupyter-prototype-уровня решений.
2. **Слой доступа к данным абстрагирован.** Все запросы к event log идут через интерфейс `EventLogRepository`. В MVP — единственная реализация на PostgreSQL. Архитектурно предусмотрено добавление ClickHouse без переписывания бизнес-логики.
3. **Immutable виртуальные датасеты.** Один раз созданный виртуальный датасет фиксирует версию маппинга ролей и SLA. Изменения справочников не пересчитывают историю — нужно создавать новый виртуальный датасет.
4. **Раздельная семантика данных и анализа.** Физический датасет (сырой xlsx) и виртуальный (с применёнными правилами) — две разные сущности с разным жизненным циклом.
5. **Тесты против эталонных цифр.** Все ключевые алгоритмы покрыты golden tests против синтетического датасета с заранее вычисленными метриками (см. `golden_data/`).

## Технологический стек

### Backend

- **Язык:** Python 3.11
- **Фреймворк:** FastAPI (async, OpenAPI из коробки)
- **ORM:** SQLAlchemy 2.0 (async)
- **Миграции:** Alembic
- **Валидация:** Pydantic v2
- **Аутентификация:** JWT (через python-jose) + опционально LDAP (через python-ldap или ldap3)
- **Обработка данных:** pandas 2.x, numpy
- **Process mining:** pm4py (опорная библиотека для алгоритмов)
- **Рабочий календарь:** workalendar (Russia)
- **Excel:** openpyxl (чтение xlsx), при необходимости xlsx-streaming для больших файлов
- **Очередь задач:** Celery + Redis (для фоновых задач: парсинг больших файлов, тяжёлые расчёты)
- **Тестирование:** pytest + pytest-asyncio
- **Линтинг:** ruff + mypy (strict)

### Frontend

- **Язык:** TypeScript 5.x
- **Фреймворк:** React 18+
- **Сборщик:** Vite
- **UI-библиотека:** Ant Design 5.x
- **State management:** React Query (TanStack Query) для серверных данных + Zustand для локального UI-состояния
- **Графики:** Plotly.js (для всех графиков — bar, line, heatmap, dotted chart)
- **Графы процессов:** Cytoscape.js (с расширениями: dagre layout, popper для тултипов)
- **BPMN-экспорт:** bpmn-js (генерация BPMN 2.0 XML)
- **Drag & Drop (конструктор дашбордов):** dnd-kit
- **Маршрутизация:** react-router-dom v6
- **Формы:** react-hook-form + zod
- **HTTP-клиент:** axios
- **Локализация:** русский язык по умолчанию, поддержка i18n опциональна (на будущее)

### База данных

- **СУБД:** PostgreSQL 15+
- **Доступ:** через SQLAlchemy + psycopg3
- **Поиск/фильтры:** обычные индексы B-tree, GIN для JSON-полей (атрибуты, фильтры срезов)

### Инфраструктура

- **Развёртывание:** нативно на Windows-машине разработчика (без Docker). PostgreSQL устанавливается отдельно.
- **Запуск backend:** через `uvicorn` (development) и `gunicorn` (production-like).
- **Запуск frontend:** dev-сервер Vite, production — статическая сборка, отдаваемая через nginx или встроенный StaticFiles в FastAPI.
- **Логи:** структурированные JSON-логи в stdout + ротация в файл через logrotate (Linux) или Windows-аналог.
- **Backup:** Makefile-команды `make backup` / `make restore` (pg_dump / pg_restore).
- **Process management в production:** Windows Service (через nssm) или Linux systemd.

## Глоссарий

| Термин | Определение |
|--------|-------------|
| **Лог событий (event log)** | Журнал операций бизнес-процесса. Каждое событие = одна строка с минимальным набором: case_id, activity, timestamp_start, timestamp_end. |
| **Кейс (case)** | Экземпляр процесса. В TESSA = один документ (договор, письмо, ЗНИ). |
| **Операция (activity)** | Шаг процесса, выполняемый над кейсом. В TESSA = "Согласование Юридическое управление", "Подписание Договорной отдел" и т.д. |
| **Трасса (trace)** | Последовательность операций для одного кейса. |
| **Вариант процесса (variant)** | Уникальная последовательность операций. Несколько кейсов могут иметь одинаковую трассу = один вариант. |
| **DFG (Directly-Follows Graph)** | Граф непосредственного следования операций. Ребро A→B существует, если в каком-либо кейсе сразу после A следует B. |
| **Sojourn time (длительность с учётом перехода)** | Для операции X в кейсе = `completed_X - completed_previous_in_case`. Если X первая в кейсе = собственная длительность X. Это основная метрика длительности в process mining. |
| **Rework (повтор)** | Операция встречается в одном кейсе более одного раза. **В MVP не различаем "цикл" и "повтор" — любой повтор операции = rework.** |
| **Физический датасет** | Сырой загруженный xlsx-файл. Immutable. Хранится как есть после первичной валидации. |
| **Виртуальный датасет** | Логическая интерпретация физического датасета: маппинг колонок, маппинг ролей, фильтры. Immutable после создания. Все аналитика работает поверх виртуальных датасетов. |
| **Срез** | Именованный фильтр поверх виртуального датасета. Лёгкий объект (JSON с условиями). |
| **Маппинг ролей** | Справочник `подразделение → роль` для конкретного проекта. Используется для свёртки сырых имён подразделений в семантические роли (Инициатор, Юридическое управление и т.д.). |
| **SLA-правило** | Норматив длительности для (роль, операция_паттерн). В MVP без измерения "тип документа" и "номер цикла". |
| **Проект** | Корневой контейнер для одного бизнес-процесса. Содержит общие сущности (физ. датасеты, маппинг ролей, SLA-справочник) и личные (виртуальные датасеты, дашборды, срезы). |
| **Health check** | Автоматическая проверка пригодности датасета для анализа (минимум кейсов, наличие rework, наличие нужных колонок). |
| **Golden test** | Regression-тест, проверяющий, что значение метрики на эталонном датасете совпадает с заранее вычисленным эталоном. |
| **Production calendar** | Производственный календарь РФ с разметкой рабочих/выходных/праздничных дней. Используется для расчёта SLA в рабочих днях/часах. |

## Связь с отчётами Газпром ЦПС

В качестве эталонных отчётов для проектирования визуализаций использовалась публичная презентация Газпром ЦПС "Process Mining: Исследование процессов согласования документов в TESSA". Конкретные дашборды и таблицы, которые система должна уметь воспроизводить:

- **KPI-сводка процесса** (слайды 6, 11, 16, 21): кол-во экземпляров, операций, уникальных операций, средняя длительность, период, вариативность путей, встречаемость операций.
- **Таблица повторов (ping-pong)** (слайды 7, 12, 17, 24): операция × кол-во × повторов × % rework, плюс сравнение средней длительности кейсов с повторами и без.
- **Граф ТОП-N путей** (слайды 9, 14, 19): визуализация наиболее частых трасс с указанием количества переходов и средней длительности пути.
- **Динамика операций по месяцам** (слайды 6-pravo, 11-pravo, 16-pravo, 22): столбцы = количество операций, линия = средняя длительность с учётом перехода.
- **SLA-комплаенс по операциям** (PDF "Исследование SLA по подразделениям", слайды 6-18): для каждой операции — средняя длительность с учётом перехода по месяцам vs норматив SLA + подсчёт нарушений.

Golden tests фиксируют ключевые цифры этих отчётов на синтетическом обезличенном датасете, основанном на реальной выгрузке TESSA.
