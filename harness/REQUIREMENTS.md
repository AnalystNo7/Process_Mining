# Требования: CPS Process Mining

## Сводка

- **Проект:** CPS Process Mining — инструмент анализа логов бизнес-процессов
  СЭД (TESSA) и ITSM (выявление узких мест и повторов)
- **Обновлено:** 2026-08-24 — документ создан: ретроспективное извлечение
  требований из ТЗ и кода
- **Источники требований:** ТЗ `docs/00_OVERVIEW.md` … `docs/07_ROADMAP.md`,
  задачи `docs/tasks/T01–T40`, `README.md`, код (ретроспектива as-built),
  журналы `harness/DECISIONS.md` / `harness/LESSONS.md`
- **Конвенции документа:**
  - Статусы проставлены по факту репозитория: **Проверено** = реализовано и
    покрыто тестами (golden/unit/integration); **Реализовано** = код есть,
    целевых тестов нет; **Предложено** = есть в ТЗ, в коде отсутствует;
    **Отложено** = ТЗ явно отложило. Приёмка заказчиком не проводилась.
  - Приоритеты MoSCoW — предложение аналитика с обоснованием; требуют
    ревью заказчика.
  - «Источник» — документы ТЗ (файл, раздел/строки) и/или «код
    (ретроспектива)» с указанием модуля.

## Классификация

| Префикс | Тип | Что описывает |
|---|---|---|
| BR | Бизнес-требование (Business Requirement) | Что бизнес хочет получить |
| UR | Пользовательское требование (User Requirement) | Что должен иметь возможность делать пользователь |
| FR | Функциональное требование (Functional Requirement) | Что должна делать система |
| NFR | Нефункциональное требование (Non-functional Requirement) | Производительность, безопасность, отказоустойчивость, масштабируемость, журналирование, интеграции, права доступа, ограничения качества |
| RULE | Бизнес-правило (Business Rule) | Правило обработки данных, ограничение или логика принятия решений, заданные заказчиком |
| CON | Ограничение (Constraint) | Технологическое, организационное или законодательное ограничение |

- **Обоснование:** Главная цель проекта; повторы и простои — основные потери в процессах СЭД/ITSM.
- **Источник:** docs/00_OVERVIEW.md «Цель проекта»; README.md:3-5

- **Статус:** Реализовано

- **Источник:** docs/00_OVERVIEW.md «Архитектурные принципы» п.3-4; docs/01_DATA_MODEL.md «Жизненный цикл сущностей»; docs/tasks/T15

- **Реализует:** BR-001

- **Статус:** Реализовано

- **Проверка:** Интеграционные тесты виртуальных датасетов

## RULE-001 — Метрики длительности: own, sojourn, кейс
- **Тип:** Business Rule
- **Описание:** Собственная длительность события = timestamp_end − timestamp_start. Длительность с учётом перехода (sojourn) = timestamp_end − timestamp_end предыдущего события кейса (первое событие: sojourn = own); порядок событий — по timestamp_end, затем timestamp_start. Длительность кейса = max(end) − min(start).
- **Обоснование:** Базовые определения всех расчётов длительности (ТЗ, эталон Газпром).
- **Источник:** docs/02_DOMAIN_LOGIC.md (compute_own_duration, compute_sojourn_time, compute_case_duration)
- **Приоритет:** Must Have
- **Реализует:** —
- **Зависимости:** Нет
- **Связанные требования:** FR-007, RULE-011
- **Статус:** Проверено
- **Реализация:** duration.py:9-52
- **Проверка:** golden test_duration_golden.py; unit test_duration.py
- **Открытые вопросы:** Нет
- **Комментарий аналитика:** В системе сосуществуют два порядка сортировки событий кейса (по end для sojourn, по start для трасс/DFG) — заложено в ТЗ, при равных временах даёт разные последовательности

## RULE-002 — Правила подсчёта повторов (rework)
- **Тип:** Business Rule
- **Описание:** Повтор = каждое вхождение операции в кейс сверх первого (repeats = cnt − 1 по паре кейс+операция); по операции: total = Σcnt, rework_pct = repeats/total×100; глобальный rework = Σrepeats/Σtotal×100 (эталон 20.06%); кейс «с повторами», если n_events > n_unique_activities; повторы считаются только внутри кейса.
- **Обоснование:** Методика заказчика (эталонные отчёты).

- **Зависимости:** Нет

## Конфликтующие требования

1. **RULE-011 ↔ ТЗ (SLA workdays):** ТЗ требует рабочие секунды от момента
   старта на N рабочих дней по календарю; код считает N×8 фиксированных
   часов (календарь не используется), при этом факт копится по 9 ч/день
   (окно 09–18) — завышение доли нарушений ~12.5%. Решение за заказчиком:
   подтвердить упрощение или исправить код.
2. **RULE-011 ↔ ТЗ (SLA calendar_days):** ТЗ — N×86400 календарных секунд
   против календарного sojourn; код — N×24 «рабочих» часа против рабочих
   часов: «1 календарный день» ≈ 2.7 суток. Единица фактически не работает
   по назначению.
3. **NFR-001 ↔ docs:** допуск «±1%» противоречит собственному примеру ТЗ и
   реализации (rel=0.02 для sojourn, abs=0.05 для процентов); вариативность
   в docs 89.83% vs эталон 89.91%.
4. **CON-002 внутри ТЗ:** psycopg3 (00_OVERVIEW) vs asyncpg (T01, код);
