# PLAN: Реестр требований проекта (ретроспектива)

Дата: 2026-08-24

## Шаги

1. Скопировать шаблон → harness/templates/REQUIREMENTS.md (1:1).
2. Синтезировать harness/REQUIREMENTS.md из трёх отчётов обхода
   (обзорные доки / доменная логика / API-UI-инфра): дедупликация,
   ID по префиксам, статусы по факту кода и тестов, MoSCoW с
   обоснованием аналитика.
3. Заполнить служебные разделы: конфликтующие требования (SLA-формулы,
   расхождения эталона), открытые вопросы, предположения, риски.
4. Собрать матрицу связности из карточек; проверить скриптом
   согласованность (битые ID, полнота, цепочки к BR).
5. Обновить harness/PROJECT.md (состав harness/, tasks/), коммит, пуш.

## Альтернативы

- Извлекать только из ТЗ docs/, без сверки с кодом: отвергнута — быстрее,
  но реестр не отразит as-built состояние и скроет уже найденные
  расхождения ТЗ↔код (в т.ч. вероятные дефекты SLA-формул), т.е. документ
  был бы неверен в главном — в статусах и проверяемости.
- Плоский список требований без карточек и матрицы: отвергнута — теряется
  трассировка и поля проверки/реализации, ради которых реестр и заводится.

## Риски

- 🟡 Объём документа: ~80 карточек — следим за дедупликацией (одно
  требование — одна карточка) и согласованностью матрицы (скрипт).
- 🟡 Статусы «Проверено» проставлены по наличию тестов, а не приёмки
  заказчиком — помечено в сводке документа.
- 🟢 Приоритеты MoSCoW — предложение аналитика, требует ревью заказчика.

## Бюджет

- Файлов: 5 (шаблон, реестр, BRIEF, PLAN, PROJECT.md) / Время: ~1.5 ч

- [x] красных рисков нет (или решены)
